# KMHD Playlist History

KMHD radio playlist fetcher + its public page. The session homed here is named "KMHD Playlist history".

**Deploying to teedlo.com (zero-effort rule):** the playlist pages live at https://teedlo.com/kmhd/ — `index.html` (daily playlist + "By Show"), `headnod.html` (The Headnod Show landing page), `headnod-tracklist.html` (every known Headnod track in one sortable list, linked from headnod.html's "All tracks" button), plus `playlist-utils.js`, `shows-schedule.js`, `.htaccess`, `headnod-tracks.json` (the precomputed Headnod tracklist — see below) and the `enrich/` directory of per-day Apple Music link files.

**/kmhd/ deploys from THIS repo**, not teedlo-site: push to `main` in github.com/teedlo/kmhd-playlist-fetcher-update and `.github/workflows/deploy.yml` runs `node --test`, then rsyncs each file over SSH to `teedlo.com/kmhd/`. Live in well under a minute. To add a new file to the site, add it to the `FILES` list in that workflow — the deploy uploads a fixed list, not a directory.

The teedlo-site repo (github.com/teedlo/teedlo-site, local clone ~/Documents/Projects/teedlo-site — pull before use) deploys the *rest* of teedlo.com by committing under `site/` and pushing to main (~25s). It does **not** publish /kmhd/; there is no `site/kmhd/` there. It *does* own the webroot `.htaccess`, which 301s www to the apex host.

**Apple Music links are precomputed, not looked up in the browser.** `scripts/build-enrich.js` asks KMHD for a day's playlist, looks each track up once on iTunes Search, and writes `enrich/YYYY-MM-DD.json` (exact Apple Music track/artist/album links, album art, genre, release year; `null` = no match; `"complete": false` = a run was cut short and `--backfill` will finish it). Entries are stored compact (`t`/`c`/`r` = track/album/artist ids, `a`/`h` = artwork path and host, `g` genre, `y` year; ~45 KB a day, ~18 KB gzipped) and `PlaylistUtils.expandEntry` turns them back into URLs on load; Apple Music resolves `music.apple.com/us/album/id<c>?i=<t>` with a redirect, so no slugs are stored. `compactEntry`/`expandEntry` accept either form, so old verbose files and localStorage entries still work. The pages fetch that one file alongside the day's playlist, so rows render with their exact links already in place. Every row also gets an instant Apple Music *search* link (`PlaylistUtils.searchLinks().appleMusic`), so a track with no file entry still has a working link while the old live path (shared Worker cache, then throttled iTunes JSONP) upgrades it in the background. KMHD plays ~250 tracks a day and ~90% of them are new each month, so a single global cache never covered anything; the per-day files are the whole point.

`.github/workflows/enrich.yml` runs the script on two schedules, hourly (`--days 2`, a minute or two, so a track has its exact link within an hour of airing) and every 3 hours (`--days 3 --backfill 730 --max-lookups 3000`: also repairs any day of the last two years whose file is missing or incomplete, newest first, up to ~2 h). Both commit new files as `teedlo` and call `deploy.yml` themselves (a push made with the Actions token does not fire `on: push`); they push with `git pull --rebase -X theirs` so two runs writing the same day never wedge. To change cadence or budget, edit the `cron:` lines and the `ARGS` expression in that workflow. For bulk history use `.github/workflows/backfill.yml` ("Run workflow" with a from/to date): it splits the range into 25-day slices, builds them on up to 20 parallel runners (iTunes throttles per IP, and each runner has its own), merges the slices into one commit and deploys; a two-year range takes ~4 hours. The 3-hourly run finishes any day a slice left incomplete. KMHD's archive answers back to at least 2014. To build a few dates by hand, "Run workflow" on enrich.yml with e.g. `--from 2026-01-01 --to 2026-01-31`, or run the script locally and commit `enrich/`. Reruns are cheap: the script only looks up tracks it has never seen in any existing file. iTunes tolerates short bursts but answers 403 for a few minutes after a few hundred fast calls, so the default pace is one lookup per 3.5 s and the script backs off by itself; don't "speed it up". Unit tests: `scripts/build-enrich.test.js` (run by `node --test`, which gates the deploy). The old `itunes-cache.json` snapshot is gone.

Server-side, `.htaccess` gives the day files `Cache-Control: max-age=300` (the host's default for JSON is 2 days, which would leave today's file stale) and turns on gzip for JSON (the host doesn't by default).

**The Headnod tracklist is precomputed too, separately from the day-by-day enrichment above.** `headnod-tracklist.html` used to fetch and merge every known Friday's raw KMHD playlist live in the browser (~224 requests, growing weekly) — it now just fetches one file, `headnod-tracks.json`, built daily by `scripts/build-headnod-tracklist.js` (`.github/workflows/headnod-tracklist.yml`, `30 6 * * *` UTC, a few hours after enrich.yml's hourly run has had a chance to finish that Friday night's Apple Music lookups). That script makes no iTunes calls of its own: it re-fetches each known Friday's playlist from KMHD, filters to the show's slot, and merges in whatever `enrich/<date>.json` already knows about each track (compact fields carried through verbatim). It always rebuilds the whole known range and sorts deterministically, so a day with nothing new produces a byte-identical file and commits nothing. If a given Friday's KMHD fetch fails, that date's tracks are reused from the previous `headnod-tracks.json` rather than dropped for a week. Unit tests: `scripts/build-headnod-tracklist.test.js`. To rebuild by hand, "Run workflow" on headnod-tracklist.yml, or run the script locally (`--dry-run` to preview, `--out <path>` to write elsewhere).

**Two local gotchas that look like breakage but aren't:**
- The Cloudflare Worker (`kmhd-playlist-cache.teedlo.workers.dev`) sends `Access-Control-Allow-Origin: https://teedlo.com` to *every* caller, so playlist fetches only work from that exact origin. Serving from localhost is CORS-blocked (the direct-KMHD fallback too), so verify playlist/tracklist behavior on the deployed URL. This is also why apex is canonical and www redirects to it — on www, every fetch was blocked and the pages rendered empty.
- Bump the `?v=` cache-bust on `playlist-utils.js?v=...` in **all three** of index.html, headnod.html and headnod-tracklist.html whenever playlist-utils.js changes (index.html and headnod.html also load shows-schedule.js and need that stamp bumped too when it changes — headnod-tracklist.html doesn't load shows-schedule.js at all, since slot filtering now happens server-side before it ever sees the data). A stale cached copy breaks a page silently; all three at least show a "please refresh" message if `PlaylistUtils.expandEntry` is missing.
- `PlaylistUtils.trackInSlot` reads a track's air time straight off `start.local`'s string rather than through `Date.getHours()` — that's deliberate, not an oversight: a show's slot is a fixed Portland-time broadcast concept, and `.getHours()` would read whatever timezone the *calling* code happens to run in (wrong for a non-Pacific browser, and would have zeroed out every Headnod track when scripts/build-headnod-tracklist.js started running on a UTC CI runner).
